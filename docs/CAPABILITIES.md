# Capability map and current limits

This map covers the maintained generator, generated applications and operational tooling. Configuration keys refer to [YAML v2](configuration/YAML_V2.md); generated application features remain editable code after initialization. Test evidence establishes the scenarios exercised, not a guarantee for every provider or production environment.

| Capability | How to configure or use it | Limits and recommendations |
| --- | --- | --- |
| Strict configuration and editor support | `schemaVersion: 2`; CLI `init`, `validate`, `generate`; generated JSON Schema; [validation](configuration/VALIDATION.md) | Unknown fields and old schemas are rejected. No migration converter. Parsing alone does not establish generation readiness. |
| Repository/application topology | `repositories`, backend/frontend `repository` and `path`, frontend `connectsTo`; [CLI workflow](generation/CLI_WORKFLOW.md) | Monorepo and split layouts work; paths cannot overlap. At least one backend is required. Generation requires new/empty output, mandatory Git identity and network tooling. Remote publication is optional. |
| Fixed technology stack | TypeScript, Hono, Next.js App Router, Tailwind, Drizzle, PostgreSQL/Neon, Better Auth, Query, Zustand | No arbitrary framework, ORM, database, state-library or renderer-plugin selection. Core's internal renderers are not public extension APIs. |
| Module architecture | Per-module `clean`, `hexagonal`, `onion`; [backend layouts](generation/DIRECT_BACKEND.md#architecture-contracts) | Families may coexist. Domain/application dependencies point inward. Generated source boundary checks are architectural checks, not a runtime sandbox. |
| Module communication | Explicit module `exports` and `imports`; [public contracts](generation/PUBLIC_MODULES.md) | Direct calls carry trusted context and enforce callee permissions. YAML exports currently reference endpoint-backed operations only. Imports do not invent orchestration, transactions, events or cross-backend calls. |
| Persistence and database ownership | Named `databases`, backend `persistence`, module-owned entities; [YAML entity reference](configuration/YAML_V2.md#5-entities-fields-and-data-ownership) | One dedicated database per persisted backend; no sharing between backends or multi-database transaction support. R2 sharing follows different rules. |
| Entity schema and query behavior | Fields, enums, constraints, defaults, timestamps, indexes, relations, seeds, soft deletion, endpoint projections/joins | Relations and joins stay within a module. Many-to-many generation and stored-FK cycles fail readiness/validation. Scalar IDs do not provide referential checks or public module calls. Review SQL and seed suitability. |
| Business HTTP operations | Explicit `endpoints`, path/query/body bindings, response and pagination; [API screens](generation/API_SCREENS.md) | Entity declarations alone do not expose CRUD. Supported bindings generate operations; custom business workflows require authored code. Unsafe unguarded writes and unsupported mappings fail preflight. |
| Browser clients and forms | Connected endpoints generate typed clients, Query hooks, API Explorer and entity actions | Ambiguous automatic actions are omitted with warnings; declared operations remain in clients/Explorer. Dates cross HTTP as ISO strings; nullable response fields remain explicit. |
| State and initial reads | Query owns server data and scoped caches; Zustand owns UI state; [frontend generation](generation/DIRECT_FRONTEND.md) | Account/grant transitions clear private caches. Server list hydration is request-scoped and does not replace backend authorization. Never store sessions in a parallel UI store. |
| Theme and responsive shell | Per-frontend `theme`, light/dark palettes, Light/Dark/System control | Main palette colors are all-or-none per mode. Status overrides default separately. Check custom contrast; no arbitrary runtime palette editor. |
| Authentication and account journeys | Backend `authentication`: email/username credentials, SMS OTP, supported OAuth, session/password policies, recovery, phone linking; [setup](generation/AUTHENTICATION.md) | Requires persistence and delivery/provider secrets where applicable. Feature configuration is not proof of complete provider-specific enrollment UI. Company-domain restrictions require verified company email before phone linking. |
| Abuse controls | `rateLimit` IP/account budgets, `smsOtp` daily quotas/cooldowns | Database-backed enforcement survives restarts. Apply migrations first. SMS reservations are consumed even if delivery fails. No CAPTCHA, global spending cap or DDoS guarantee. |
| Dynamic IAM | Initial YAML roles/grants, generated `/admin/roles`, platform IAM routes, `auth:create-admin`; [IAM](generation/IDENTITY_ACCESS.md) | One server-owned role per account; live database grants, no ABAC/multi-role engine. Seeds preserve existing role edits. Default/system/last-admin protections apply. |
| Frontend page access | `access.mode`: public, authenticated, mixed; explicit identity authority; [page access](generation/FRONTEND_ACCESS.md) | Page visibility and API permissions are separate. One authority per frontend; no cross-backend SSO. Authored pages need explicit guards. Cookie presence alone is never verification. |
| Audit logging | Endpoint `audit: true`; automatic auth/IAM events; protected `/audit` Activity page; [audit guide](generation/AUDIT_LOGGING.md) | Asynchronous best effort, no durable queue/retries/delivery guarantee. Capture is not a business transaction. Review retention and business-data visibility in the client project. |
| AI chat and shared tools | Backend/frontend `ai`, provider secrets, optional `AI_MODEL`; [AI/MCP](generation/AI_MCP.md) | One AI backend per project with persistence/authentication. Permissions are checked live; chat history has ownership and size limits. Check provider model availability separately. |
| External MCP clients and custom tools | Public gateway Worker, OAuth/PKCE and scoped personal keys, exported `*.tool.ts` | Private business backend stays private. Gateway uses Streamable HTTP, not separate legacy SSE endpoints. MCP mutation confirmation is a client declaration; custom code must preserve authorization. |
| R2 and document management | Root/backend `iac`, OpenTofu, `StoragePort`, `/r2`; [infrastructure](INFRASTRUCTURE.md) | Private by default; public custom domains need zones. Direct uploads are bounded to 100 MiB and require signing/CORS. No automatic business-file registry, orphan cleanup or object ownership policy. |
| Local Docker | Per-repository Compose, app images, PostgreSQL/proxy, Mailpit, local R2/MCP when configured | No hot reload. Synthetic seeds run once. `docker:down` deletes local volumes; ordinary Compose down preserves them. Local R2 signing is not automatically cloud-equivalent. |
| Deployment and placement | Generated `cicd:setup`, native Cloudflare builds, OpenNext, private bindings, backend placement; [deployment](DEPLOYMENT.md) | `develop` is staging, `main` production. Setup runs after publication. Placement does not increase CPU/memory or guarantee latency; measure real workloads. No generated GitHub Actions deployment runner. |
| Infrastructure changes | Generated OpenTofu state, environment tfvars, native PR plans and apply | State has one owner; deploy owner before split consumers. Merging can delete buckets and their contents automatically. Back up/migrate before destructive changes. |
| Recovery and maintenance | Committed migrations, generated `DISASTER_RECOVERY.md`, Neon PITR | Retention depends on the account plan. Test restore procedures and measure recovery objectives. Off-site R2 database backups and automatic application rollback are not provided. |

## Verification boundaries

The [contributor guide](CONTRIBUTING.md) lists focused and full checks. Unit/compiler suites verify configuration, generation and selected runtime behaviors. Persistence suites use isolated PostgreSQL through a local Neon HTTP proxy. Commerce acceptance generates fresh applications and exercises database/browser/session behavior. Docker acceptance covers monorepo and split operation.

Live OAuth delivery, arbitrary external MCP clients, actual cloud costs/quotas, production latency and complete disaster recovery still need verification in the destination environment. Existing tests do not justify promising those outcomes. For an unsupported mapping, simplify the initial configuration and implement the needed behavior in the generated application; do not bypass readiness by inventing YAML fields.
