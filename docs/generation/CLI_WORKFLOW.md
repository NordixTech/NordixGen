# CLI workflow and verification

Use Node.js 24+ and pnpm 10.5.2. In a development checkout, run `pnpm install --frozen-lockfile` and `pnpm build` before invoking `node packages/cli/dist/index.js`.

`init` asks for the project name, optional frontend and configuration location. It emits canonical YAML v2 with a persisted Clean `examples` module, a constrained `Example.name`, declared public list/create operations and pagination. It checks the same generation readiness as `validate` and `generate` before writing. Cancellation and existing configuration files remain protected. The starter does not silently create login requirements or remote repositories.

`generate -f nordix.config.yaml -o ./new-project` resolves once through core, prepares direct backend/frontend output, rejects unsafe/nonempty destinations and checks tooling/repository prerequisites before scaffolding. Split repositories get independent pnpm workspaces. Dependencies and their categories come from the core renderers; unrelated upstream entries survive. Unexpected file/script/dependency-category collisions fail explicitly.

Pinned official Hono and Next.js scaffolders run in isolated temporary workspaces with a relative application target. Hono's pinned CLI requires its own installation; only source is copied into the final project, excluding its temporary dependencies, Git metadata and lockfiles. Next.js skips its preliminary install. Each completed repository then installs once with its final manifest/workspace. The CLI runs strict application typechecking (including Next route type generation) and backend module-boundary checks before optional publication. It reports failures by stage/application, includes actual compiler output and masks credentials. External failure can leave local output for inspection; generation does not promise atomic rollback or overwrite edited projects.

Generated README/environment examples explain local setup. For host-based development, set backend runtime values in `.dev.vars` and frontend public origins in `.env.local`. Database commands also need `DATABASE_URL` in the Node shell: `pnpm db:generate`, review SQL, `pnpm db:migrate`, then optional `pnpm db:seed`. Scripts point to `src/platform/database`. With identity, migrations initialize IAM roles/grants; register an operator normally and run `pnpm auth:create-admin operator@example.com` in the backend to promote the existing account. Role changes are subsequently managed through the protected `/admin/roles` page. Without identity, explicitly configure `CORS_ALLOWED_ORIGINS`; with Better Auth, configure its URL and trusted origins. Multiple backends need distinct ports and explicit matching client/identity URLs. Real secrets and build/dependency outputs are ignored by Git; blank environment examples remain tracked.

## Local Docker environments

Every generated repository includes `docker-compose.yml`, `.dockerignore` and root package scripts:

```bash
pnpm docker:up    # docker compose up -d --build
pnpm docker:logs  # docker compose logs -f
pnpm docker:down  # docker compose down -v: deletes local database volumes
```

Docker Engine with Compose v2 is sufficient to start an already generated checkout using `docker compose up -d --build`; host Node/pnpm is not required for this command. Generation itself still requires the tooling described above. Use `docker compose down` to stop while preserving data. Containers are exclusively for local development and use standalone/build output without source hot reload.

Each frontend/backend has its own three-stage Dockerfile, built with its repository root as context and the final repository pnpm lockfile. Next.js standalone tracing covers the workspace; static/public assets are copied explicitly and the server runs as a non-root user. Browser requests remain same-origin through the frontend BFF. Server calls use named Cloudflare service bindings or explicitly configured private local Docker transport.

Each persisted backend owns a PostgreSQL 16 Alpine service, volume and Neon HTTP proxy. The generated local Node adapter supplies Worker bindings and execution context, waits for migrations and seeds before listening, and leaves the Worker entry point available for its existing workflow. The CLI prepares initial migration SQL once during generation; keep its journal/SQL in Git. Docker images reuse that stable history, and startup applies pending SQL and initializes IAM roles. After schema changes, generate and review new migrations before building. Synthetic seeds run once per database, tracked in `nordix_local_bootstrap`. A failed/interrupted seed leaves a pending marker and blocks automatic re-seeding: inspect the database before recovering, or discard only a disposable local volume. This prevents restart-time duplicate records. Business seeds do not create login accounts. Promote an existing registered operator using `auth:create-admin` with the same database connection; optional provider/email journeys still need their credentials.

Host ports default to 8787+ for backends, 3000+ for frontends and 5432+ for persisted backends, following resolved project order. Override `BACKEND_<NAME>_PORT`, `FRONTEND_<NAME>_PORT`, `POSTGRES_<BACKEND>_PORT` in the repository-root `.env` to avoid collisions with other projects. Names are uppercase with hyphens changed to underscores. Override `BACKEND_<NAME>_PUBLIC_URL`, `BACKEND_<NAME>_TRUSTED_ORIGINS` and `BACKEND_<NAME>_AUTH_SECRET` as appropriate. Default passwords/secrets are development-only; environment files and build outputs are excluded from image contexts.

Split repositories run their own services on a shared project-named private bridge. Start the first backend repository before consumers. Backend host ports are disabled by default; the generated docker-compose.debug.yml enables loopback debugging explicitly.

From this generator checkout, `pnpm example:docker monorepo` and `pnpm example:docker split` generate fresh applications, build/boot the emitted environments, exercise real database/API/browser/session behavior and verify data/seed persistence after restarts. The split fixture puts both applications at their repository roots. Both layouts run in CI; logs, screenshots and results are retained under ignored `tmp/docker-acceptance/`. These checks clean up only their uniquely named Compose resources.

Git initialization and GitHub publication are configured opt-ins. Publication requires local Git initialization, an available identity, authenticated GitHub CLI, the configured organization handle and a new remote name. All local application checks finish first. The CLI creates the remote without pushing, verifies the actual origin and branch, then performs a dry-run push before the real push. Ordinary automated tests use injected repository commands; a separate disposable local Git test verifies tracked files and secret exclusions without creating remote repositories.

Focused tests cover useful starter readiness, early rejection without process effects, split/root application placement, dependency ownership, upstream integration failures, failure containment, compiler diagnostics, remote destination verification and credential redaction. Core checks execute the public no-identity CORS middleware and compile generated forms with both simple and absent operations. Separate real-scaffolder checks run the built CLI's validation/generation commands for backend-only and full-stack starters using the pinned tools and real dependency installations. The full-stack output passes a production Next.js build; its actual backend migrates and verifies create, invalid input rejection, filtering, pagination and allowed browser CORS against an isolated disposable PostgreSQL database through the Neon HTTP adapter. The shared persistence suite also exercises seeds and real session policies.

The maintained [commerce example](../../examples/full-stack-commerce/README.md) verifies fresh public-CLI generation, application compilation, Worker bundling, real PostgreSQL migrations/seeds, HTTP authorization, browser forms and account-cache isolation. Run `pnpm example:commerce` from the repository root; each run writes revision, environment and stage/behavior results into a new ignored `tmp/examples/full-stack-commerce/<id>/` directory. This verifies the supported local topology, not cloud deployment or every optional identity-provider journey.

## Native Cloudflare CI/CD and Neon

Every generated repository contains an initial main commit and develop pointing to it. Git identity is a prerequisite; initializeGit=false is rejected. Remote creation remains opt-in and publishes both branches with an atomic push. Generated README files document two setup options: pnpm cicd:setup (standalone CLI, no installed generator required) and manual Cloudflare/Neon configuration in docs/DEPLOYMENT.md. Public account profiles are kept in ignored .nordixgen files; credentials are masked input or shell environment values.

Native Cloudflare builds target develop -> staging and main -> production. Backend checks run before committed Drizzle migrations, then deployment; frontend builds use OpenNext for Workers. Monorepos and split repositories use their own repository-root commands. Account setup is a separate operation after GitHub publication. Neon Managed Auth is not enabled; Better Auth remains inside the backend. Frontend same-origin /api routing is generated using private service bindings. PITR procedures document plan-specific retention and measured recovery objectives; off-site R2 backups remain excluded.
