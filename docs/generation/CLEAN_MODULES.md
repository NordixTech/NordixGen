# Clean business modules

Each backend now generates one modular monolith with module-owned domain entities/enums, application DTOs/use cases/ports, Drizzle adapters and declared controllers under `src/modules/<name>/`. There is no parallel global business-layer output. Scoped render contexts select resolved ownership; they do not parse or infer ownership from entity names. Used domain enums are local to their module and introduce no private cross-module imports.

Platform identity, authorization, HTTP problems/routes, database client and migration/seed helpers are emitted once under `src/platform/`. Business tables and relations live under each module's `infrastructure/database/schema/`; the platform schema aggregates those exports, shared PostgreSQL enums and identity tables once. The explicit composition creates one business database client and supplies that instance to all module bootstrap factories through module-scoped query types. One Hono application mounts the declared operations from all modules. Platform composition can import module bootstrap/controller implementations; another business module cannot.

Module `index.ts` is the [public application boundary](PUBLIC_MODULES.md). Explicit typed exports/imports, trusted context, application results and direct wiring are implemented. Hexagonal/Onion and many-to-many still fail shared preflight before effects. Modules cannot import the all-table platform schema or bypass their scoped database type.

## Enforced boundaries

The generated `scripts/check-boundaries.mjs` uses the TypeScript syntax tree. `pnpm run check:boundaries` rejects infrastructure/HTTP imports into domain/application, another module's deep private imports, undeclared public dependencies and private exports from a module entry. Errors identify consumer, producer/reference, location and correction. Literal dynamic imports/require are checked too; computed imports must be replaced with static declared contracts. This is an architectural source check, not a runtime sandbox for arbitrary authored code.

The CLI runs it after package installation and before Git/GitHub operations. The maintained tests execute the checker on clean output, then deliberately insert invalid inward/private/undeclared imports and private exports and require failure.

## Evidence and limits

Two independent persisted Clean modules compile with real Hono, Drizzle, Neon and Better Auth dependencies in CI. This found and corrected loss of insert-field types and duplicate foreign-key seed assignments. Existing executable generated-handler checks now use module paths, including a two-module request fixture; both implicit HTTP CRUD and entity-derived application/repository CRUD artifacts are absent. CLI checks verify one backend scaffold, both modules and the executable boundary command.

Application/public contract communication and generated trusted context are implemented. A shared process/client does not imply a shared transaction or automatic business calls. CI now generates real Drizzle migrations, applies them through Neon HTTP to an isolated PostgreSQL database, seeds deterministic business fixtures without auth accounts, and executes generated HTTP mutations/queries and declared operation ports. It covers decimal/null/default conversion, aliases, main/related filters, literal contains, projected relations, inner/left joins, active-row counts, soft deletion and sanitized constraint conflicts. It also migrates an intentionally unauthenticated schema and exercises bounded unique/one-to-one seeds. The integrated commerce example additionally covers the connected product.

To run database acceptance locally, use a disposable PostgreSQL database named `nordixgen_test` with the `nordixgen_test` user and a local Neon HTTP proxy. Set `NORDIXGEN_TEST_DATABASE_URL` explicitly to `postgresql://nordixgen_test:<test-password>@db.localtest.me:5432/nordixgen_test` and `NORDIXGEN_TEST_PROXY_PORT` to the proxy's local port (default `14444`). The suite refuses any other host/user/database and resets that isolated database. It never selects an ambient `DATABASE_URL` as its target. CI supplies both services and runs this suite as part of the required check; without the explicit opt-in, local runs skip database acceptance.

The maintained [commerce example](../../examples/full-stack-commerce/README.md) verifies fresh public-CLI generation, application compilation, Worker bundling, real PostgreSQL migrations/seeds, HTTP authorization, browser forms and account-cache isolation. Run `pnpm example:commerce` from the repository root; each run writes revision, environment and stage/behavior results into a new ignored `tmp/examples/full-stack-commerce/<id>/` directory. This verifies the supported local topology, not cloud deployment or every optional identity-provider journey.
